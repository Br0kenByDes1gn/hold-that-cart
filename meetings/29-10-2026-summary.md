## Focus of the meeting

A working session on **how to test the two uncertain parts of the product**: real-model photo scanning and the pantry/prediction logic. The approach is to use snapshot ("golden data") testing rather than building custom freeze logic.

## Agreed: two test tracks

### 1. Real-model scan tests — Zaro

- Keep a **folder of real photos**: receipts, products, and possibly the physical shopping cart.
- Run them through the **actual vision model**, not a stub or mock.
- Review the model output before freezing anything.
- Present every result in **two forms**:
  - **JSON** — the snapshot / golden data that gets saved.
  - **HTML preview** — a human-readable view for judging whether the recognition makes sense.
- Use the test framework's built-in **snapshot mode**; no need to design a custom snapshot mechanism.
- If the output is good, save/replace the snapshot. If not, fix the test or adjust the prompt and re-run.

### 2. Prediction tests — schmithvillers

- Generate **synthetic pantry data** covering several different scenarios, for example:
  - a pantry with only **1 receipt**,
  - a pantry with **2–3 receipts**,
  - a pantry with **10 receipts**.
  - The exact number does not matter; the point is to cover a few non-identical cases.
- The data can be plain JSON, but it must match the **structures already defined in the code** — the input shape the existing algorithm expects.
- Do **not** invent a new schema or algorithm. Inspect the code, describe the test case, and ask the model to generate data in that shape.
- Start by generating **2–3 scanned receipts** in the same shape the pantry stores them.
- Run the existing prediction algorithm on the data.
- Generate an **HTML preview of the predictions** as well — reading raw JSON is much harder to judge.
- Review the preview, iterate, and **snapshot** the output once it looks sensible.
- The generated data can be kept if it is good enough, or replaced with better/real data later.

### Shared principles

- **Review before freezing.** Snapshots are only saved after a human judges the output.
- **JSON for storage, HTML for judgement.** Both tracks should produce a readable preview.
- **Use what already exists.** The prediction work must plug into the current code structures and algorithm; nothing new needs to be invented.
- **Keep it simple.** The task is essentially moving data around and testing the algorithm; Zaro warned that AI tends to propose overcomplicated solutions that are not needed.

## Discussed but not agreed / still open

- **Test framework choice** — explicitly "doesn't matter", as long as it supports snapshots; no specific tool was fixed.
- **How the HTML preview is generated or served** — the need is agreed, the implementation is not.
- **Exact scenario set and fixture counts** — 1 / 2–3 / 10 receipts were examples; the final coverage is deliberately flexible.
- **Fate of the synthetic fixtures** — keeping them permanently vs replacing them with real or better-generated data is deferred until they can be reviewed.
- **Source of the real photos** for the scan suite — the folder has to be assembled, but where the images come from was not specified.
- **How often real-model scans run** — real API calls cost credits and are non-deterministic; whether they run in CI or only manually when refreshing snapshots was not discussed.
- **Scope of the prediction tests** — whether they cover only the rhythm/stock-state engine or the full suggestion pipeline (BUY/SKIP/SWAP, tags, money) was not pinned down.
- **Model configuration for the scan tests** — "the actual model" is the intent, but the exact model/version/settings were not fixed.
- **CI integration** — neither suite was explicitly wired into a pipeline; only the local review/snapshot loop was discussed.
