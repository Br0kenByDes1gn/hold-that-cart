## Product ideas agreed in principle

1. **"Hold that cart" as the differentiator.** When a list or cart is scanned, check it against the pantry first and show "You already have N of these" at the top. Rules by shelf life:
   - **Perishables** (days: milk, bread, vegetables) — never "you already have this"; only swaps.
   - **Staples** (weeks: rice, oil, flour) — soft flag if recently bought, with an estimate.
   - **Household consumables** (1–3 months: detergent, soap) — flag when recently bought.
   - **Durables** (years: bottles, containers, cutlery, bags) — strongest "hold that cart" alert.
   - The four-category table is accepted as a **starting point**; categories may be extended later. The key requirement is to exclude perishables from repeat-purchase logic.
2. **Three suggestion groups instead of per-item suggestion spam:**
   - **BUY** — due/rebuy; already sustainable, just buy it again.
   - **SWAP** — a good alternative exists.
   - **SKIP** — probably still have it, or no replacement found.
   - Shown as three simple visual indicators; clicking an item lets the user act ("I need it", "Skip it") to finalise the list. This greatly simplifies the UI.
3. **Suggestion timing / learning model:**
   - `T` = typical interval between purchases; `d` = days since last purchase.
   - `d < 60% of T` → probably stocked (SKIP candidate); `60–100%` → getting low; `> 100%` → due (BUY).
   - 60% is a **starting heuristic**, to be tuned with real usage data; it only works after a few purchases.
   - A **pre-shop briefing** appears when the user taps "Start shopping" or opens the scanner.
4. **Cold start behaviour:**
   - **Day 0:** only swap suggestions plus applicable tags from a scanned list/cart — no history needed.
   - **After 1 receipt:** "due soon" estimates from category defaults.
   - **After 2–3 receipts:** personal rhythm.
5. **Tag display:** show only the tags that actually apply (**saves money / healthier / sustainable**); leave the rest greyed out. No percentages and no long "why" explanations in the list — keep it simple.
6. **Grounding:** the model should not invent products or prices; suggest **types/forms** (loose instead of packaged, refill, store brand, larger pack) rather than made-up brands.
7. **Trust and corrections:**
   - Per-item **"I'm out"** and **"Never remind me"** belong in the Pantry, not as global pre-shop buttons.
   - Only flag items with enough history, and label things as estimates ("probably").
   - Everything must be correctable — habits change and the app cannot predict everything.
8. **Account types:** **Household** and **Business** are chosen at signup as two separate account types, not a toggle (users rarely switch). Both have the same features; Business simply makes **analysis more prominent**. There is **no separate business pantry screen**.
9. **Screens:**
   - Keep the existing start → scanner → pantry flow and add the pre-shop briefing and scan-results screen.
   - The current screen/button table is too simplistic: each screen needs its **function** described, not just its buttons. Filter chips, "Analyse", etc. need proper definitions.
   - A separate document describing screen functions and actions will be written; the first generated app will only include basic functionality, with full actions added later.
10. **Design and assets:**
    - Produce a **design file with the visual language**, plus **separate reusable asset files** (not one document).
    - Assets should be icons/images **without backgrounds or borders** — HTML will handle the chrome.
    - Start with **20–50 product icons** plus generic fallbacks (unidentified item, food, cleaning). Having more than needed is fine.
    - ChatGPT is preferred over Claude for generating image assets.
    - All design/algorithm/behaviour docs should live as **markdown in the repo**, with images as separate files (not embedded, which bloats the markdown).
11. **Technical approach:**
    - Reuse the **same architecture as Ecosight**.
    - Zaro builds a **bare-bones backend first, with no visuals**; the frontend then layers the design on top.
    - There is **no Meta hosting**; deploy on schmithvillers' account/server and use the Meta API with the credits.
12. **Working split:**
    - **Zaro:** backend, generation prompts, deployment walkthrough.
    - **schmithvillers:** design, assets, frontend, reviewing the backend and asking questions.
    - Testing and prompt tuning will be the bottleneck; both will do testing/polish sessions together.

## Discussed but not agreed / still open

- **Exact shelf-life categories and thresholds** — four categories are a starting point; whether more are needed, and whether 60%/100% are the right cut-offs, is unresolved.
- **Pre-shop briefing limits** — the doc proposes top 8 BUY, top 3–5 SKIP, top 3 SWAP, with "See all 27 items"; the meeting did not settle these caps.
- **Kitchen/pantry shelf photo** to auto-detect what's missing and build a list — described as "a good option… just an option", never committed.
- **Email at signup vs local-only data** — Zaro leaned toward collecting an email immediately so data can be saved, but explicitly said "I'm not sure". Account/data persistence is undecided.
- **"Verify the saving"** — counting savings only when a later receipt confirms the item wasn't bought; Zaro said this needs experimentation, and the wording should be softened.
- **Health and sustainability data sources** — Open Food Facts coverage and a proprietary sustainability score were proposed in the doc but not discussed or accepted in the meeting.
- **Definition of "Analyse"** — the doc proposes money saved vs baseline, health-score change and sustainability-score change; the meeting only touched on the screen and filter chips.
- **Business mode specifics** — Cart/order-check/invoice screens, seeded demo data, and what "analysis more prominent" means in practice are all unreviewed.
- **Hosting and its architectural impact** — Cloudflare Workers are short-lived (no long-running server), which changes the design; Google/AWS/Azure free tiers and Zaro's Helm-based server are all still candidates.
- **How much screen functionality goes into the first generation** — Zaro plans to leave most of it out until the screen-actions document exists.
- **New-user onboarding questions** — household size and shopping frequency were proposed in the doc but not agreed.
- **Novelty brainstorm is not finished** — schmithvillers called the additions "just my thought"; more ideas may still be added.
- **Muse quality and cost** are unknown; the team may fall back to another model mid-project.
- **Asset scope/style** — how many product icons, and whether to generate everything up front or only on demand, was left open ("assets, you can go crazy").
